# tensorrt-triton-inference-template

A benchmark harness for inference runtimes that **refuses to make numbers up**.

Point it at a model and it measures every runtime the machine can actually run —
PyTorch, ONNX Runtime, TensorRT, Triton — reports latency percentiles and
throughput for each, and checks that the fast ones still compute the same answer
as the slow one. A runtime it cannot run gets a row saying *why*, never a figure.

That last rule is the reason this exists. Comparison tables of inference
backends are easy to write and almost never measured; this one starts empty and
fills in only what it observed.

## Quick start

```bash
python3 -m venv .venv && ./.venv/bin/pip install -r requirements.txt
PYTHONPATH=src ./.venv/bin/python -m inferbench.cli bench --batch 1
```

No GPU required — the harness measures whatever is present and says what is not.
On an NVIDIA box, add `-r requirements-gpu.txt` and the TensorRT and Triton rows
fill themselves in.

Direct dependencies are pinned in `requirements.txt` and
`requirements-gpu.txt`; the Linux x86_64/Python 3.12 dependency resolution is in
`uv.lock` and is generated by uv from `pyproject.toml`. `benchmark.lock.json`
is a human-readable benchmark manifest (commands, container image, GPU/driver
prerequisites and schema metadata), not a dependency lock. Neither lock can
replace the host NVIDIA driver or GPU.

For the locked Linux x86_64 / CPython 3.12 environment, use `uv sync --locked`
for CPU tests. GPU installation via `uv sync --locked --group gpu` is unverified:
the pinned TensorRT 10.3.0 PyPI source package can invoke a nested pip download
of NVIDIA libraries and bindings, which `uv.lock` does not fully resolve or hash.
The package's own metadata also describes that release as intended for TensorRT-LLM.
Verify the chosen NVIDIA packages, binary versions, driver, and install on the
target system before treating it as a reproducible GPU environment.
Run the CPU-capable test suite with `uv run --locked python -m unittest discover -s tests -v`.
The pip quick start above pins direct dependencies only, not transitive packages.

## Measured

Apple M1, macOS, ResNet-18, batch 1, 100 iterations after 20 warm-up:

```
backend                  p50 ms   p99 ms     inf/s    max |Δ|   top-1
--------------------------------------------------------------------
pytorch-cpu               23.82   111.18      36.4  reference       —
pytorch-mps                7.47    20.33     124.4   6.68e-06  100.0%
onnxruntime-cpu           36.00    90.27      24.3   6.20e-06  100.0%
onnxruntime-coreml         1.62    11.68     511.6   1.20e-02  100.0%
pytorch-cuda                  —        —         —   unavailable: no CUDA device
onnxruntime-cuda              —        —         —   unavailable: CUDAExecutionProvider not built into this wheel
tensorrt-fp16                 —        —         —   unavailable: tensorrt not installed
triton-http                   —        —         —   unavailable: tritonclient not installed
```

### The ranking changes with batch size

| backend | b=1 p50 | b=8 inf/s | b=32 inf/s |
| --- | ---: | ---: | ---: |
| pytorch-cpu | 23.82 ms | 47.4 | 20.5 |
| pytorch-mps | 7.47 ms | 253.9 | 222.2 |
| onnxruntime-cpu | 36.00 ms | 25.9 | 24.9 |
| onnxruntime-coreml | **1.62 ms** | **1256.8** | **1583.0** |

ONNX Runtime on CPU is the **slowest** backend at batch 1 and **beats PyTorch
CPU** at batch 32. PyTorch CPU's throughput peaks at batch 8 and then falls.
A single headline number cannot express either of those, which is why the
harness separates latency (batch 1 — what one caller waits) from throughput
(large batch — what the hardware delivers) and sweeps between them.

### Speed has a precision cost, and it is measurable

CoreML is 15× faster than the PyTorch CPU reference. It is also the only backend
whose numerical drift is visible:

| backend | max abs difference | top-1 agreement |
| --- | ---: | ---: |
| pytorch-mps | 6.68e-06 | 100% |
| onnxruntime-cpu | 6.20e-06 | 100% |
| onnxruntime-coreml | **1.20e-02** | 100% |

Three to four orders of magnitude more drift than the FP32 backends, because the
Apple Neural Engine computes in reduced precision. Top-1 still agrees here, but
that is a property of this model and this input — not a guarantee. Every speed
number in this repository is paired with the drift that bought it, and the same
column is what will hold TensorRT's FP16 and INT8 engines to account.

## Two bugs the harness caught in itself

**Every backend ran a different model.** The first run reported `max |Δ| = 9.65`
and **0% top-1 agreement** for all three backends. Not drift — the model factory
initialised fresh random weights on every call, so the ONNX file, the reference
and each backend held different networks. The accuracy column existed for
exactly one run before it earned its keep. `build_torch_model` now seeds, and a
test asserts two builds are bit-identical.

**Async runtimes lie about latency.** A GPU backend that returns as soon as work
is queued measures the enqueue, not the compute — and looks spectacular. Every
backend's `infer()` is required to synchronise before returning: `mps.synchronize`,
`cuda.synchronize`, `cudaStreamSynchronize` for TensorRT. Triton and ONNX Runtime
are blocking already.

## Green inference: energy per successful inference

On a supported NVIDIA GPU, install `requirements-gpu.txt` and opt in to board
energy measurement:

```bash
PYTHONPATH=src python -m inferbench.cli --model resnet18 bench --batch 32 \
  --iterations 200 --warmup 30 --energy --energy-idle-seconds 5
```

The harness reads NVML's cumulative GPU energy counter in millijoules before and
after the measured inference loop; it does not estimate from a short-window
power reading. The optional `nvidia-ml-py` dependency is required. NVIDIA lists
the counter as supported on Volta-or-newer fully supported devices; if the
binding, driver, GPU, or counter is unavailable, the result says so and emits no
energy number. See the [NVML device query reference](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceQueries.html).

Each successful run reports raw GPU-board joules per successful output row and,
separately, an idle-baseline-adjusted value. The idle baseline is measured before
the backend runs. NVML measures the *whole physical GPU*, so other processes or
co-tenants can contribute; these are board-energy figures, not process-level or
whole-system energy, and they do not include CPU, memory, or cooling power. A
remote Triton server is not attributed to the client machine. Use
`--assume-triton-local-gpu` only when Triton is actually running on the measured
local GPU. Unsupported counters remain explicitly unavailable rather than
falling back to approximate values.

The run also reports p95 latency and exact successful inference rows. Model,
batch, and native TensorRT FP32/FP16 rows are available in the existing
harness. Triton queue delay is configurable with
`triton-repo --max-queue-delay-us`; regenerate and restart the model repository
for each queue-delay setting rather than treating it as a client-only request
setting. Triton response caching requires both a model-side switch and a
server-side cache allocation; the repository generator emits both when asked:

```bash
PYTHONPATH=src python -m inferbench.cli triton-repo --max-queue-delay-us 100 \
  --response-cache --cache-size-bytes 268435456 --out model_repository
```

The benchmark supports deterministic `--request-pattern unique` (the default)
and `--request-pattern repeat`. Use unique inputs for ordinary inference and
repeat inputs to measure a hot-cache workload; warm-up requests use the same
pattern, so repeated inputs are already cache hits when timing starts. For a
Triton run, declare the server settings so they appear in JSON:

```bash
PYTHONPATH=src python -m inferbench.cli bench --only triton-http \
  --request-pattern repeat --triton-response-cache enabled \
  --triton-cache-size-bytes 268435456 --triton-max-queue-delay-us 100
```

These are declared server settings, not auto-discovered facts. The current
benchmark sends one blocking request at a time, so it does not exercise dynamic
batching or measure queue-delay effects; `--triton-max-queue-delay-us` records
the declared server setting only. Queue-delay comparisons require a concurrent-
load benchmark, which is not implemented yet. The harness also does not scrape
Triton cache hit/miss metrics, so verify the server launch and use Triton metrics
for hit-rate analysis. Response caching is appropriate for repeated requests;
unique-input results are the cache-miss workload. Real GPU energy and cache-hit
measurements remain follow-up work.

## The GPU path

Both GPU backends are written and neither has been run in this checkout — there
is no NVIDIA device, TensorRT, or Triton client installed here, and the harness
says so rather than estimating. On a CUDA box:

```bash
./.venv/bin/pip install -r requirements-gpu.txt
PYTHONPATH=src python -m inferbench.cli bench --batch 32     # trt rows fill in
PYTHONPATH=src python -m inferbench.cli export
PYTHONPATH=src python -m inferbench.cli triton-repo --platform tensorrt_plan \
  --plan artifacts/engines/resnet18-fp16-b32.plan --out model_repository
docker run --gpus=all --rm -p8000-8002:8000-8002 \
  -v $PWD/model_repository:/models nvcr.io/nvidia/tritonserver:24.08-py3 \
  tritonserver --model-repository=/models
PYTHONPATH=src python -m inferbench.cli bench --batch 32 --only triton-http
```

`tensorrt-fp16` builds the engine from the ONNX graph directly rather than going
through ONNX Runtime's TensorRT execution provider. The EP is more convenient,
but it silently falls back to CUDA for any layer TensorRT will not take, which
mixes two runtimes into one measurement. Building the engine means what runs is
TensorRT or nothing.

For `--platform tensorrt_plan`, `--plan` is mandatory. The source must be a
readable regular file; the repository writer creates parent directories, copies
the bytes atomically to `<model>/1/model.plan`, and verifies the copied bytes.
Missing, unreadable, or unwritable paths fail loudly. An ONNX repository uses
the same verified copy path for `model.onnx`.
Byte verification does not validate the engine's model, TensorRT/driver/GPU
compatibility, I/O names, dimensions, or optimization profile; ensure the plan
matches the generated config and target Triton environment before serving it.

## `config.pbtxt`, and the two ways to get it wrong

`inferbench triton-repo` generates the model repository. Both of these produce a
server that starts cleanly and then misbehaves:

- **`max_batch_size > 0` makes the batch axis implicit.** `dims` must then
  describe one sample *without* it. Include it and the model loads and rejects
  every request.
- **`dynamic_batching` is off by default**, and it is most of what makes a
  server fast. `max_queue_delay_microseconds` is a real latency/throughput dial,
  not boilerplate.

Both are covered by tests.

## Layout

```
src/inferbench/
  model.py            ResNet-18 + ONNX export, deterministic weights, dynamic batch
  backends/
    base.py           the contract: available() / load() / infer() / close()
    torch_backend.py  cpu · mps · cuda
    ort_backend.py    CPU · CoreML · CUDA · TensorRT execution providers
    trt_backend.py    native engine build + execution        (CUDA only)
    triton_backend.py HTTP client                            (server required)
  bench.py            warm-up, percentiles, latency vs throughput
  energy.py           NVML GPU-board energy counter; unavailable when unsupported
  accuracy.py         cross-backend agreement against the reference
  triton_repo.py      model repository + config.pbtxt
  report.py           the table, and the JSON behind it
```

New results land in `results/bench-b{N}.json` and conform to the copied
`benchmark-results.schema.json` (schema version `1.0.0`). They include git
state, software/host/GPU metadata, deterministic parameters, and raw timing
samples in seconds. Unavailable or failed backends have empty samples and a
reason. The three checked-in `results/bench-b*.json` files are legacy Apple M1
measurements: they predate this schema, have no original execution timestamp
or Git metadata, and are not reproducible GPU results. They are retained as
historical provenance and are intentionally not converted or schema-validated.
The full shared rules are in `BENCHMARK_STANDARD.md`.

The result statistics use the raw samples in seconds: `median` is the true
`statistics.median`, and `stdev` is population standard deviation
(`statistics.pstdev`) for the complete sample set. A completed measurement
must have samples; unavailable and failed backends retain an explicit status,
reason and empty samples.
